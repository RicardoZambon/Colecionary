02 · Arquitetura

Como as peças se encaixam

Uma imagem Docker com um processo. Dentro dela, uma solução .NET em quatro projetos com dependências em uma direção só, e um SPA Angular estático servido do wwwroot do mesmo host. Esta página descreve a topologia, as camadas, a ordem do pipeline HTTP — que é carga estrutural, não estética — e o que acontece no boot.

Topologia

Produção: uma imagem, uma porta

O Dockerfile tem três estágios: compila o SPA com Node 22, publica a API com o SDK .NET 10, e copia os dois para uma imagem aspnet:10.0 — o SPA vai para ./wwwroot. O contêiner fala HTTP puro na porta 80; TLS termina no proxy reverso de quem hospeda. Só linux/amd64: SQL Server não tem build ARM. 

docker run -d --name colecionary \
  -p 8080:80 \
  -v colecionary-config:/data/config \
  ricardozambon/vault:latest
O volume das imagens não está declarado

A imagem declara VOLUME ["/data/config"], mas não declara nada para as imagens. O padrão de ImageStorage:Root é App_Data/images, relativo ao content root do app — ou seja, dentro da camada de escrita do contêiner. Recriar o contêiner sem montar esse caminho perde todas as fotos enviadas. Em qualquer implantação real, monte um volume e aponte ImageStorage__Root=/data/images. Veja Deploy → persistência.

Desenvolvimento: dois servidores

Em desenvolvimento o SPA roda no dev server do Angular (:4200) e a API em :5100, portanto cross-origin. Isso não é um detalhe: é o motivo pelo qual a política de CORS precisa expor cabeçalhos de resposta explicitamente. Sem WithExposedHeaders, script cross-origin não lê ETag (e toda gravação após a primeira seria recusada), nem Content-Disposition (o download do arquivo perde o nome escolhido pelo servidor), nem Retry-After (o SPA não sabe quanto esperar depois de um 429).

Camadas do backend

Clean architecture com quatro projetos. A regra é a direção das setas: nada aponta para dentro do Domain, e Domain não referencia nada.

O caminho de uma requisição

  1. Controller — valida forma, lê If-Match via IfMatch.Require(Request), chama o serviço, devolve ETag. backend/src/Vault.Api/Controllers/
  2. Application service — regra de negócio, comparação de versão, mapeamento DTO↔entidade, exceções de domínio traduzidas (NotFoundException, ConflictException, PreconditionFailedException…). backend/src/Vault.Application/
  3. Repository — só mecânica de EF: Include, ReplaceGraph, MergeByKey. Nunca escreve filtro de tenant. backend/src/Vault.Infrastructure/Persistence/Repositories/
  4. VaultDbContext — aplica o filtro global por convenção, dispara os interceptors no SaveChanges e traduz DbUpdateConcurrencyException em PreconditionFailedException. backend/src/Vault.Infrastructure/Persistence/VaultDbContext.cs

Ordem do pipeline HTTP

A ordem em Program.cs não é cosmética. Três posições têm razão escrita e teste que falha se forem trocadas.

PosiçãoPor quêSe inverter
UseForwardedHeaders antes de tudo Tudo abaixo que pergunta “quem é quem chamou” tem que receber a mesma resposta — o throttle acima de todos. Atrás de proxy reverso, todos os chamadores caem no mesmo bucket: 30 logins falhos de qualquer um responde 429 para a implantação inteira.
UseRequestLocalization antes de UseExceptionHandler O handler monta o título enquanto a exceção sobe o pipeline; a cultura precisa ainda estar em escopo. Erro em português vira erro em inglês. LocalizationTests falha.
Throttle de login dentro da action, não em middleware Precisa do e-mail submetido, que só existe depois do model binding — e precisa estar a jusante da localização para o 429 sair traduzido. Ou não tem o e-mail, ou responde em inglês.
Estáticos antes de auth O shell do SPA é público; só /api exige token. A política deny-by-default devolve 401 na página de login.
Fallback /api/{**path} antes do fallback do SPA Um segmento literal é mais específico que o catch-all, então uma rota de API inexistente responde 404 JSON. O SPA sequestra rotas de API e devolve index.html com 200 — o cliente recebe HTML onde esperava JSON.

Sequência de boot

Program.cs tem um laço de host em volta da construção da aplicação, porque o wizard de primeiro uso reconstrói o host no mesmo processo do SO — assim a senha do admin e a chave JWT gerada só existem em memória até o bootstrap do banco dar certo.

  1. Resolver o diretório de configuração — Setup:ConfigDirectory (na imagem, /data/config).
  2. Existe connection string? Provedores normais (appsettings, ambiente, user-secrets) ganham. Só se nenhum fornecer, consulta colecionary.json persistido e a configuração encenada pelo wizard.
  3. Não → host de setup. Host mínimo: serve o SPA e /api/setup/*, protegido por um token de uso único que é logado no console. Sem DbContext, sem auth. Já com UseRequestLocalization, porque antes de existir banco ou usuário o Accept-Language é a única pista de idioma. Vault.Api/Setup/SetupEndpoints.cs, SetupCoordinator.cs
  4. Sim → host completo. Registra controllers, ProblemDetails, Application, Infrastructure, JWT, autorização deny-by-default, CORS. O coletor de imagens só é registrado se ImageGc:Enabled for true — desligado ele não fica ocioso, ele não existe.
  5. LegacyImageBlobExporter.ExportAsync() — antes de qualquer migration. Copia blobs remanescentes da coluna varbinary(max) para o IImageStore, para que a migration MoveImageBytesToFileStorage possa derrubar a coluna em seguida. No-op em todo boot posterior.
  6. Bootstrap do banco — no caminho do wizard cria o primeiro tenant + owner e persiste a configuração; senão, se Seed:Enabled, roda o DbSeeder (que também migra); senão apenas Database.Migrate().
  7. Se o host encenado falhar (banco ruim, migration quebrada), a falha é registrada, a configuração pendente é descartada e o laço volta ao modo setup — com a mensagem aparecendo no próximo render do wizard.
Nunca aplique migrations com dotnet ef nesse caso

MoveImageBytesToFileStorage derruba a coluna de bytes, e uma migration não escreve arquivos. A exportação vive no startup, então dotnet ef database update contra um banco que ainda guarda blobs apaga os bytes. Suba a API: ela faz as duas coisas, na ordem certa.

Precedência de configuração

Da maior para a menor prioridade. O ponto importante é o último item: a configuração do wizard só é consultada quando nenhum provedor normal fornece connection string, o que torna a implantação headless sempre determinística.

  1. Linha de comando (--Chave=valor)
  2. Variáveis de ambiente (ConnectionStrings__Vault, Jwt__SigningKey, ImageStorage__Root…)
  3. User secrets (só em Development)
  4. appsettings.{Environment}.json
  5. appsettings.json
  6. {Setup:ConfigDirectory}/colecionary.json — apenas se nada acima trouxer connection string

Camadas do frontend

A direção é features → shared → core. core não importa nada de shared nem de features; componentes de shared/ui não falam com a API nem com stores — com duas exceções deliberadas, ui-image-focus e ui-toast, que existem justamente para renderizar o estado de um serviço de core. 

frontend/src/
├─ styles/
│  ├─ _themes.scss     ← TODOS os tokens visuais (7 temas)
│  └─ _mixins.scss
└─ app/
   ├─ core/            ← sem UI
   │  ├─ models/       tipos do domínio (espelham os DTOs)
   │  ├─ api/          VaultApi (contrato) + HttpVaultApi, ImagesApi, ArchiveApi
   │  ├─ auth/         AuthService, interceptor, authGuard
   │  ├─ setup/        SetupService + guards do wizard
   │  ├─ i18n/         I18nService, dicionários, interceptor de idioma
   │  ├─ state/        VaultStore, Theme, Toast, ImageFocus, PhotoUpload, Conflict, Currency
   │  └─ utils/        funções puras, todas com spec
   ├─ shared/
   │  ├─ ui/           A biblioteca de componentes (ui-*)
   │  └─ pipes/        t, money, itemValue
   ├─ layout/          shell, topbar, sidebar, conflict-notice
   ├─ features/        páginas roteadas, lazy, uma pasta por feature
   ├─ app.routes.ts
   └─ app.config.ts    ← DI: { provide: VaultApi, useClass: HttpVaultApi }

Toda página roteada é loadComponent (lazy). O app é zoneless: estado em signals, componentes OnPush, sem padrões dependentes de Zone.js. Detalhes em App Angular.
