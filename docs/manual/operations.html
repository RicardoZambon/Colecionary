Deploy, configuração e suporte

Uma imagem, uma porta, um banco que você fornece. Esta página é a referência operacional: o que configurar, o que precisa de volume, como o release acontece, o que fazer antes de restaurar um backup e a tabela de sintomas.

Rodar a imagem

docker run -d --name colecionary \
  -p 8080:80 \
  -v colecionary-config:/data/config \
  -v colecionary-images:/data/images \
  -e ImageStorage__Root=/data/images \
  ricardozambon/vault:latest

Abra http://<host>:8080/. TLS termina no proxy reverso; o contêiner fala HTTP puro na porta 80. Só linux/amd64. Você fornece o SQL Server (2022+).

O que precisa sobreviver ao contêiner

CaminhoGuardaDeclarado na imagem?Se não montar
/data/config colecionary.json: connection string + chave JWT gerada sim O wizard roda de novo a cada recriação, e todas as sessões caem (chave JWT nova)
ImageStorage:Root Todos os bytes de imagem, um diretório por tenant não Todas as fotos são perdidas na recriação do contêiner. O padrão App_Data/images é relativo ao content root, ou seja, dentro da camada de escrita
SQL Server Tudo o mais externo —
Monte o volume de imagens explicitamente

A imagem declara VOLUME ["/data/config"] e não declara nada para imagens. Em qualquer implantação real, monte um volume e aponte ImageStorage__Root para ele. Sem isso, a arquitetura de “bytes fora do banco” — que existe para tornar backup e cota possíveis — entrega exatamente o contrário: um backup do banco que não contém as fotos, e um contêiner que as leva embora ao ser recriado.

Primeiro uso

  1. Sem connection string, o app entra em modo setup e imprime um token de uso único no log: docker logs colecionary → procure SETUP MODE — … token ….
  2. Abra o app; ele redireciona para /setup. Informe o token, depois a conexão do SQL Server (o login precisa de direito de criar o banco se ele não existir), a primeira organização + conta owner, e o tema padrão.
  3. Aplicar cria o schema e a conta owner, grava /data/config/colecionary.json e reinicia no login normal.
  4. Reconfigurar depois: apague colecionary.json do volume.

Pular o wizard (configuração headless)

docker run -d --name colecionary -p 8080:80 \
  -v colecionary-config:/data/config \
  -v colecionary-images:/data/images \
  -e ConnectionStrings__Vault="Server=db-host,1433;Database=Colecionary;User Id=sa;Password=…;TrustServerCertificate=true" \
  -e Jwt__SigningKey="um-segredo-aleatorio-longo-de-pelo-menos-32-bytes" \
  -e ImageStorage__Root=/data/images \
  ricardozambon/vault:latest

Backup e restore

Não existe backup automático em lugar nenhum do sistema. Um backup completo tem duas partes que precisam concordar:

  1. O banco SQL Server (backup nativo do SQL).
  2. O diretório de ImageStorage:Root, inteiro.
Antes de restaurar: desligue o coletor

A varredura acredita no banco sobre o que existe e no storage sobre o que está em disco. Restaure um sem o outro e todo arquivo que o banco restaurado esqueceu lê como lixo mais velho que a carência, porque rsync -a e afins preservam a data de modificação. Coloque ImageGc:Enabled em false (ou DryRun de volta em true) até saber que as duas partes concordam.

Para dados de um usuário específico existe também GET /api/export (zip do tenant com fotos) e POST /api/import para restaurar. Isso é autoatendimento pelo app, não substituto de backup de infraestrutura: ele é por tenant e roda no contexto de uma sessão.

Pipeline de release

.github/workflows/release.yml roda em todo push para main, em pull requests e por disparo manual.

O que o job de validação roda, em ordem

  1. Guarda: “todo projeto de teste da solução está coberto abaixo” — falha alto se alguém adicionar um terceiro projeto sem adicionar o passo.
  2. dotnet build -c Release — avisos são erros.
  3. dotnet format --verify-no-changes.
  4. Testes unitários do backend, com TreatNoTestsAsError=true.
  5. npm ci, npm test -- --watch=false, npm run build.
  6. Testes de integração (SQL Server via Testcontainers) — por último de propósito: é o único passo que precisa de Docker e o único que pode falhar por motivo que não é o código.
Por que tudo num job só

Proteção de branch exige um check por nome, e só um admin do repositório adiciona nomes àquela lista. Um portão movido para um job próprio deixaria de ser obrigatório no instante em que se mudasse, em silêncio, e nada neste arquivo diria isso. O custo é rodar em série. Pague.

E nunca adicione TESTCONTAINERS_RYUK_DISABLED ou TESTCONTAINERS_HOST_OVERRIDE ao CI: essas variáveis existem só num dev container cujo Docker alcança o SQL Server pelo host, e no CI desligariam o reaper que limpa depois de uma execução cancelada.

Versionamento = conventional commits

Prefixo do commitEfeito

A versão é estampada em Vault.Api.csproj e frontend/package.json no job publish, que verifica os dois depois de escrever. A imagem sai como ricardozambon/vault:<versão> e :latest.

Sintomas e causas

SintomaCausa provávelO que fazer
“O wizard de setup roda toda vez” /data/config não está montado Monte o volume. Depois de configurado, a rota /api/setup/status nem é mapeada
“Todas as fotos sumiram depois de atualizar” ImageStorage:Root na camada de escrita do contêiner Não há recuperação sem backup. Monte volume e aponte ImageStorage__Root
“Todo mundo foi deslogado” Jwt:SigningKey mudou — inclusive por uma nova execução do wizard Restaure a chave anterior ou aceite o novo login
“Diz que alguém alterou antes, mas sou só eu” Concorrência é por coleção: outra aba, outro dispositivo, ou uma edição de item na mesma coleção Recarregar resolve. O que o usuário digitou não é descartado
“Salvei uma vez e depois todo save é recusado” O cliente não está lendo ETag — tipicamente CORS sem WithExposedHeaders num deploy cross-origin Confira Cors:Origins e que ETag está exposto
“429 para todo mundo, sem ataque nenhum” Proxy reverso na frente sem ForwardedHeaders:KnownProxies: todos no mesmo bucket Nomeie o proxy. Só o endereço do proxy, e apenas um hop
“Login lento / API demorada no login” Sem índice em Email sozinho: todo login varre a tabela Limitação conhecida. O pré-portão evita que tentativa recusada chegue ao SQL
“O arquivo baixado tem nome genérico” Content-Disposition não exposto no CORS Confira a política. Aparece primeiro no export de uma coleção
“Uma imagem carrega enorme num card pequeno” Chamada sem variante nomeada Use images.url(id, 'thumb'). Duas URLs = duas entradas de cache
“GIF parou de animar” Não deveria: GIF nunca é derivado Se acontecer, alguém mudou SkiaImageDeriver.CanDerive
“Imagem some sozinha depois de um tempo” Coletor ligado e fora de dry run, e a imagem realmente ficou sem referência a carência inteira Confirme ImageGc. Uma restauração parcial de backup é a outra causa
“Import não sobrescreveu o que eu escolhi” A versão da coleção alvo se moveu entre o plano e a confirmação O 409 traz um plano novo — responda contra o que está no vault agora
“Membro convidado não consegue entrar” PasswordHash nulo; não existe fluxo de convite Limitação conhecida da v1
“Um deploy zerou o bloqueio de força bruta” O estado do throttle é em memória Limitação conhecida; a forma durável é uma tabela

Notas de atualização

  • Sempre suba a API para migrar. MoveImageBytesToFileStorage derruba a coluna de blobs, e a exportação para o storage vive no startup, antes de Database.Migrate(). dotnet ef database update contra um banco que ainda guarda blobs apaga os bytes.
  • Migrations são aplicadas automaticamente no boot. Não há passo manual — e não há downgrade.
  • colecionary.json é lido apenas se nenhum provedor normal fornecer connection string, então uma implantação headless é sempre determinística.
  • index.html nunca é cacheado (no-cache, no-store, must-revalidate); um deploy não deixa clientes presos a um shell velho referenciando bundles com hash que já foram removidos.
